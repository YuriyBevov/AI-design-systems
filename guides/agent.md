# Гайд для ИИ-агентов

Этот документ описывает правила работы ИИ-агентов с техническим заданием, дизайн-макетом, контентом и кодом проекта.

Цель гайда — не допускать самовольных решений, которые меняют смысл макета, структуру интерфейса или текст без прямого указания.

## Источник истины

Главные источники истины:

- техническое задание;
- дизайн-макет;
- существующие проектные гайды;
- уже утвержденная структура проекта.

При верстке агент всегда руководствуется актуальными гайдами из папки `guides`. Эти документы обязательны к применению и имеют приоритет над привычками агента, типовыми шаблонами и субъективными улучшениями.

Если агент пишет стили, он соблюдает mobile-first подход: базовая версия должна быть мобильной, а правила для больших экранов добавляются как расширение.

Если агент переносит размеры из макета в CSS или SCSS, он не использует нечётные значения в `px` для размеров, отступов, координат, ширин, высот и типографики. Нечётное значение всегда приводится к ближайшему меньшему чётному значению: `19px` становится `18px`, `13px` становится `12px`, `3px` становится `2px`. Исключение допускается только для технических `1px` в `border`, `outline` и скрытых accessibility-паттернах.

Если между источниками есть противоречие, агент не должен придумывать решение молча. Нужно явно отметить противоречие и выбрать самый безопасный вариант: сохранить данные из ТЗ или макета без расширения.

## Не добавлять лишние элементы

Агент не добавляет элементы, которых нет в техническом задании или дизайн-макете.

Это касается:

- текстовых блоков;
- заголовков;
- кнопок;
- иконок;
- декоративных элементов;
- изображений;
- ссылок;
- полей формы;
- оберток без явной необходимости;
- вспомогательных UI-элементов.

Если элемент кажется полезным для семантики, доступности или удобства, но его нет в ТЗ или макете, агент не добавляет его самостоятельно. Допустимы только технически необходимые атрибуты и невидимые для пользователя улучшения, которые не меняют интерфейс и содержание.

Плохо:

```html
<span class="footer-nav__title">Доставка</span>
```

Если такого заголовка нет в макете или ТЗ, его не должно быть в разметке.

### Названия слоёв и групп не являются контентом

Названия фреймов, групп, колонок и слоёв в макете используются только для понимания структуры. Их нельзя переносить в HTML как видимый текст.

Текст добавляется в разметку только тогда, когда он существует в макете или ТЗ как самостоятельный текстовый объект, который должен быть виден пользователю. Если в макете группа называется `Footer Column Доставка`, `Footer Column Контакты`, `Navigation` или похожим образом, это имя группы, а не заголовок для верстки.

Плохо:

```html
<div class="footer__delivery">
	<span class="footer__nav-title">Доставка</span>
	<ul class="link-list">...</ul>
</div>
```

Хорошо:

```html
<div class="footer__delivery">
	<ul class="link-list">...</ul>
</div>
```

Перед добавлением любого видимого текста агент должен проверить, что это именно текстовый слой/контент из ТЗ, а не название контейнера, группы или слоя в дизайн-файле.

## Не менять текст

Агент никогда не переписывает, не расширяет и не сокращает текст из технического задания или дизайн-макета по своему усмотрению.

Запрещено:

- менять формулировки;
- добавлять новые предложения;
- удалять части текста;
- заменять тональность;
- улучшать маркетинговый смысл;
- уточнять текст без запроса;
- добавлять пояснения, которых не было в источнике.

Допустима только аккуратная орфографическая правка, если она не меняет смысл, стиль, объем и структуру текста.

Плохо:

```text
Исходный текст: Оставьте заявку
Текст агента: Оставьте заявку, и наш менеджер свяжется с вами в течение 15 минут
```

Хорошо:

```text
Исходный текст: Быстрое сроки производства
Правка: Быстрые сроки производства
```

Если есть сомнение, является ли изменение текста орфографической правкой или уже редактурой, агент должен сохранить исходный текст и предложить замену в файле agent-suggestions.md.

### Регистр текста

Если текст в макете набран заглавными буквами, в HTML-разметке он переводится в обычный регистр: заглавной остается только первая буква в начале предложения. Визуальный капс, если он нужен по макету, задается через CSS, а не через текст в HTML.

Исключение — аббревиатуры, краткие технические обозначения и устоявшиеся сокращенные названия. Если такое название принято писать заглавными буквами, в HTML оно сохраняется заглавными буквами: например, `ТПЛ`, `ПВХ`, `ГОСТ`.

Плохо:

```html
<button class="button">ОСТАВИТЬ ЗАЯВКУ</button>
```

Хорошо:

```html
<button class="button">Оставить заявку</button>
```

### Ручные переносы строк

Тег `<br>` по умолчанию запрещен. Агент не использует `<br>` для управления визуальным переносом заголовков, кнопок, карточек, CTA-блоков или другого интерфейсного текста.

Переносы строк должны задаваться CSS: шириной контейнера, `max-width`, `display`, `white-space`, `text-wrap`, flex/grid-раскладкой или другими стилевыми средствами.

`<br>` допустим только в крайних случаях, когда перенос является частью самого содержания, а не визуального оформления: например, в почтовом адресе, стихотворной строке, юридически заданной формулировке или другом тексте, где ручной перенос должен сохраниться независимо от ширины экрана. Если есть сомнение, `<br>` не используется.

Плохо:

```html
<h2 class="section-title">Преимущества,<br />которые работают</h2>
```

Хорошо:

```html
<h2 class="section-title">Преимущества, которые работают</h2>
```

### Неразрывные типографские связки

В HTML-тексте используются неразрывные пробелы для коротких и смыслово связанных фрагментов, которые не должны разрываться переносом строки.

Для HTML используем сущность `&nbsp;`.

Неразрывный пробел ставится:

- после предлогов: `в&nbsp;каталог`, `для&nbsp;упаковки`, `на&nbsp;рынке`;
- после коротких союзов `и`, `или`: `и&nbsp;аксессуары`, `или&nbsp;товары`;
- внутри составных союзов и после них, если следующий фрагмент связан по смыслу: `а&nbsp;также&nbsp;аксессуары`;
- после частицы `не`: `не&nbsp;порвутся`, `не&nbsp;стирается`;
- между числом и следующим словом или единицей измерения: `14&nbsp;дней`, `10&nbsp;мб`, `2010&nbsp;года`;
- между частями сокращений и служебных обозначений, если они должны читаться вместе;
- вокруг тире в текстовых связках, где части фразы должны оставаться рядом: `НьюМарк&nbsp;—&nbsp;каталог`, `2&nbsp;дня&nbsp;—&nbsp;скидка`.

Плохо:

```html
<span class="product-card__conditions">Минимальная партия — 3 коробки · срок — 14 дней</span>
```

Хорошо:

```html
<span class="product-card__conditions">Минимальная партия&nbsp;—&nbsp;3&nbsp;коробки · срок&nbsp;—&nbsp;14&nbsp;дней</span>
```

Правило применяется только к видимому тексту: заголовкам, описаниям, кнопкам, пунктам навигации, подписям форм и placeholder. Внутри тега `head` и в метатегах неразрывные пробелы не используются: `title`, `meta description`, `meta keywords`, Open Graph, Twitter Card и другие служебные данные пишутся с обычными пробелами. Если фрагмент уже связан неразрывным пробелом, повторно его не менять.

## Предложения по улучшению

Если в процессе работы у агента появляются предложения по улучшению, он не внедряет их самостоятельно и не смешивает с основной задачей.

Такие предложения фиксируются в отдельном файле внутри папки текущего проекта.

Название файла:

```text
agent-suggestions.md
```

В этот файл можно выносить:

- замечания по структуре;
- идеи по улучшению доступности;
- предложения по упрощению разметки;
- возможные улучшения дизайна;
- рекомендации по текстам;
- технические долги;
- вопросы, которые требуют решения владельца проекта.

Файл с предложениями не заменяет техническое задание и не дает агенту права менять макет или текст без отдельного запроса.

## Дневник проекта

При работе над проектом агент ведет структурированный дневник проекта.

Дневник хранится внутри папки текущего проекта.

Название файла:

```text
agent-conversation-history.md
```

В дневнике фиксируются:

- основные этапы работы над проектом;
- что было сделано на каждом этапе;
- для чего выполнялись изменения;
- какие правила и договоренности были добавлены или уточнены;
- какие файлы и области проекта затрагивались;
- важные технические решения;
- проверки, которые выполнялись после изменений.

Дневник не должен быть дословной стенограммой переписки. Его задача — сохранять проектную память: структурированно описывать ход работы, причины решений и текущее состояние проекта так, чтобы к нему можно было вернуться позже и быстро понять контекст.

Если дневник уже существует, агент обновляет его по мере значимых изменений. Если дневника нет, агент создает его в папке проекта при первой необходимости или по прямому запросу.

## Правило по умолчанию

По умолчанию агент переносит макет и ТЗ максимально буквально.

Любое улучшение, которого нет в источнике, считается изменением требований и не выполняется без отдельного запроса.
