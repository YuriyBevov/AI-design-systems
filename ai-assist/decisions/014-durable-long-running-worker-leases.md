# ADR-014: Устойчивые lease для долгих system jobs

## Статус

Принято, 2026-09-17.

## Контекст

Парсинг сайта может выполняться несколько часов, а один provider request — до пяти минут. Стандартный
30-секундный BullMQ lock оказался слишком чувствительным к временной задержке event loop, Redis и
development reload: job переходил в stalled, повторно запускался и после исчерпания стандартного
лимита помечался `failed`, хотя первоначальный processor продолжал сохранять результаты в PostgreSQL.

PostgreSQL остаётся источником истины для crawl progress, а обработка страниц уже идемпотентна через
page checkpoints. Тем не менее преждевременный повтор job создаёт лишние запросы и расход provider.

## Решение

- System worker использует lock длительностью 10 минут и обновляет его раз в минуту.
- Stalled-проверка выполняется раз в минуту.
- До окончательного `failed` допускаются три восстановления stalled job.
- Верхнеуровневая concurrency worker остаётся равной двум; внутренние fetch/AI лимиты не меняются.
- Потеря renewal и восстановление stalled job получают отдельные структурированные журнальные события.
- При reload worker выполняет graceful close: перестаёт брать новые jobs, но ждёт завершения текущих.

## Последствия

- Кратковременная задержка event loop или Redis не приводит к параллельной обработке одного crawl.
- Реальное падение worker обнаруживается медленнее: возврат job в очередь может занять до 11 минут.
- Несколько последовательных аварий не уничтожают run сразу, а page checkpoints исключают повторную
  AI-нормализацию уже сохранённых страниц.
- Изменение исходного кода development worker во время crawl применится только после graceful
  завершения активной задачи.
