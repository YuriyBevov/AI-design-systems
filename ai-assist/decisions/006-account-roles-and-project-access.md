# ADR-006: продуктовые роли и доступ к проектам

- Статус: принято
- Дата: 2026-09-09

## Контекст

Первоначальная техническая модель `Owner/Editor/Viewer` задавала права отдельно для каждого проекта. Для текущего продукта достаточно двух понятных ролей аккаунта, а назначение пользователя на проекты должно управляться из одного раздела панели и при создании проекта.

## Решение

Публичная продуктовая модель содержит ровно две роли:

- `Администратор` (`admin`) — полный доступ к панели и всем существующим и новым проектам;
- `Пользователь` (`user`) — доступ на чтение только к назначенным проектам; технический раздел «Компоненты» и управление пользователями ему недоступны.

Роль хранится в `users.role` и входит в серверную сессию. Назначение пользователя на проект хранится в `project_memberships`. Для совместимости с уже реализованными project-scoped проверками администратор получает внутреннюю membership `owner`, а пользователь — `viewer`. Значение `editor` остаётся в PostgreSQL enum как техническая совместимость миграций, но новый продуктовый API его не принимает и не создаёт.

При создании или повышении администратора сервер назначает его владельцем всех неархивированных проектов. При создании проекта все активные администраторы включаются автоматически, а выбранные обычные пользователи получают read-only membership. Отключение пользователя отзывает его активные сессии. Последнего активного администратора нельзя отключить или понизить.

## Последствия

- UI и публичные DTO не показывают `owner/editor/viewer` как роли продукта.
- Список проектов обычного пользователя формируется только из его memberships.
- Управление проектами, пользователями, секретами и публикацией остаётся за администраторами; серверные проверки действуют независимо от скрытия элементов UI.
- Возврат редактирующей роли потребует отдельного продуктового решения и расширения внешнего контракта, а не повторного показа внутреннего `editor`.
