# ADR-008: устойчивые и управляемые crawl runs

- Статус: принято
- Дата: 2026-09-15
- Дополняет: [ADR-005](005-ai-normalized-raw-site-ingestion.md),
  [ADR-007](007-editable-crawl-normalization.md)

## Контекст

Длинная ИИ-нормализация использовала 60-секундный лимит на весь streaming response. Ответ мог
поступать штатно, но обрывался по общему таймеру. Формат JSON задавался только текстовой
инструкцией, поэтому редкий ответ с дополнительным текстом отклонялся целиком. Оператор также не
мог приостановить большой обход или повторно скачать одну изменившуюся либо ошибочную страницу.

## Решение

1. Provider adapter поддерживает `response_format`; нормализация запрашивает строгий JSON Schema и
   сохраняет локальную runtime-валидацию результата. Если выбранная модель отклоняет structured
   output с HTTP 400, единственный повтор выполняется без `response_format`.
2. Для crawl AI-вызова разделены общий лимит запроса и idle timeout. Общий лимит по умолчанию —
   300 секунд, idle timeout — 60 секунд и сбрасывается при каждом полученном фрагменте stream.
3. Невалидный модельный ответ, `PROVIDER_BAD_RESPONSE` и retryable provider error получают не более
   одного повтора. Это восстанавливает временно оборванный/повреждённый stream, ограничивает
   стоимость и не превращает постоянную ошибку в бесконечный цикл.
4. Crawl run хранит `pause_requested_at`. Worker проверяет состояние перед каждой новой страницей и
   ожидает продолжения, не теряя уже обработанные результаты и внутреннюю очередь адресов.
5. Точечный повтор создаёт отдельный run с одним сохранённым URL. Страница заново скачивается с
   теми же SSRF, robots и origin-ограничениями, затем проходит обычную ИИ-нормализацию.
6. Редактор normalization prompt временно исключён из render tree локальным UI-флагом; CSS-классы
   скрытия оставлены как дополнительная защита. Prompt продолжает храниться в настройках и run
   snapshot; API повторной AI-only обработки не удаляется.
7. Окончательная остановка разрешена только из паузы. API атомарно переводит run в `cancelled`, а
   worker между страницами подтверждает выход через `finished_at` и возвращает успешный queue result
   со статусом `cancelled`, не помечая источник ошибочным. Удаление разрешено только после этого
   подтверждения и затрагивает run с page results, но не созданные документы БЗ. Если остановленный
   job после перезапуска worker вернулся в `waiting`, чтение run безопасно удаляет его из очереди и
   фиксирует завершение; `active` job таким способом не прерывается.
8. Для моделей с reasoning crawl-нормализация запрашивает `reasoning_effort=low`: задача состоит в
   извлечении и форматировании фактов, поэтому скрытое рассуждение не должно вытеснять итоговый
   JSON из output budget. Бюджет crawl-ответа составляет 20 000 токенов. Завершение provider stream
   с `finish_reason=length` получает отдельный код `CRAWL_AI_OUTPUT_TRUNCATED`, а не маскируется под
   невалидный JSON.

## Следствия

- Длинный активный stream больше не считается зависшим только из-за общей продолжительности.
- Зависший stream всё ещё прерывается idle timeout, а каждый запрос имеет конечный общий предел.
- Пауза применяется после текущей страницы; уже выполняющийся provider call не обрывается.
- Точечный повтор недоступен, пока для того же источника идёт другой run.
- Pause polling занимает активный worker slot; перенос checkpoint очереди в Redis/БД остаётся
  возможным расширением для длительных production-пауз.
- Между запросом остановки и подтверждением worker UI показывает отдельное состояние
  «Останавливается» и не разрешает удаление, исключая гонку с записью текущей страницы.
