# ADR-011: ограниченно-параллельный crawl pipeline

- Статус: принято
- Дата: 2026-09-17
- Дополняет: [ADR-005](005-ai-normalized-raw-site-ingestion.md),
  [ADR-008](008-resilient-and-controllable-crawl-runs.md)

## Контекст

Один crawl run последовательно загружал страницу, ждал полную ИИ-нормализацию, сохранял результат и
только затем переходил к следующему URL. На больших сайтах основное время занимало ожидание provider,
а сетевой crawler оставался без работы. Простые пакеты по несколько страниц ухудшают точечные повторы:
одна ошибка или timeout заставляет повторять пакет целиком.

## Решение

1. Один crawl run выполняется как bounded pipeline независимых страниц без пакетирования:
   технический fetch и AI-normalization имеют отдельные лимиты параллельности.
2. По умолчанию одновременно выполняются не более двух fetch и пяти AI-вызовов. Лимиты задаются
   server-side переменными `KNOWLEDGE_CRAWL_FETCH_CONCURRENCY` и
   `KNOWLEDGE_CRAWL_AI_CONCURRENCY`; допустимые диапазоны — `1..10` и `1..20`.
3. `requestDelayMs` и больший `Crawl-delay` из robots остаются общим ограничителем начала запросов
   одного run. Параллельность не разрешает начинать запросы к сайту чаще установленной задержки.
4. Очередь сырых страниц ограничена обратным давлением: fetch не накапливает весь сайт в памяти,
   если пять AI-операций уже заняты.
5. AI-лимит разделяется всеми одновременно выполняемыми crawl runs одного worker process. Два
   system jobs не умножают число provider-вызовов выше заданного значения.
6. Каждая страница сохраняется и получает ошибку независимо. Счётчики run обновляются атомарными
   приращениями, поэтому завершившиеся не по порядку страницы не могут откатить progress.
7. Пауза прекращает запуск новых fetch. Уже начатые fetch и AI-вызовы завершаются; окончательная
   остановка остаётся кооперативной.
8. BullMQ может повторно получить run, оставшийся в состоянии `running` после падения worker. Такой
   run восстанавливает счётчики из page results, повторно строит очередь ссылок и пропускает уже
   сохранённые URL на AI-этапе; URL/checksum identity дополнительно защищает документы от дублей.

## Следствия

- Типичное ускорение ограничено самым медленным этапом, robots delay и лимитами provider; пять
  параллельных AI-вызовов не гарантируют пятикратное ускорение.
- Это асинхронные операции ввода-вывода, а не пять системных потоков Node.js.
- Технический fetch остаётся частью одного BullMQ run job. Отдельный persistent BullMQ job на каждую
  страницу потребовал бы page-level outbox/checkpoint и отдельного решения о восстановлении; это не
  нужно для bounded pipeline и может быть добавлено позже при горизонтальном масштабировании.
- После аварийного перезапуска текущая in-memory очередь URL строится заново. Уже сохранённые
  страницы могут быть повторно скачаны ради восстановления link discovery, но не проходят повторную
  AI-нормализацию.
