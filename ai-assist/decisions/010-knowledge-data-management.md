# ADR-010: явное управление и очистка данных базы знаний

- Статус: принято
- Дата: 2026-09-16
- Дополняет: [ADR-008](008-resilient-and-controllable-crawl-runs.md)

## Контекст

Панель показывала только последний crawl run источника, удаляла только полностью остановленный run
и не выводила уже существующее удаление записи БЗ. Оператор не мог увидеть всю историю или очистить
данные проекта без прямого доступа к PostgreSQL.

## Решение

1. Панель показывает до 5 000 crawl runs проекта в обратном хронологическом порядке. Любой
   терминальный run можно удалить отдельно; queued/running run сначала нужно остановить.
2. Удаление crawl run очищает его page results и оставшийся terminal BullMQ job, но сохраняет
   созданные документы БЗ.
3. Подтверждённое удаление документа очищает его версии, публикации, chunks, products, embeddings и
   ссылки `widget_generation_sources`. Сообщения диалогов сохраняются.
4. Owner получает массовые действия: очистить историю, очистить записи БЗ, очистить настроенные
   URL-источники и очистить всё. Они требуют CSRF и недавнего подтверждения пароля.
5. Очистка истории блокируется при queued/running crawl или active queue job. Очистка БЗ блокируется
   во время queued/building index version.
6. Удаление одного или всех URL-источников удаляет их настройки и историю. Связанные записи БЗ
   переводятся во внутренний источник `detached-url-documents`, очищаются от внешнего идентификатора
   и сохраняются. Полная очистка `all` удаляет и записи БЗ, и URL-источники.
7. Массовая очистка не удаляет диалоги, пользователей, проект или audit events. Результат операции
   записывается в audit с агрегированными счётчиками.

## Следствия

- Оператору не нужен прямой доступ к БД для обычного управления данными.
- После удаления документа прошлый ответ виджета остаётся виден, но его техническая ссылка на chunk
  удаляется вместе с самим знанием.
- После очистки БЗ активного индекса нет; новый индекс появится после публикации новых записей и
  запуска переиндексации.
