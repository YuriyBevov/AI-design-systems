# ADR-012: очередь повторов ошибочных страниц

- Статус: принято
- Дата: 2026-09-17
- Дополняет: [ADR-008](008-resilient-and-controllable-crawl-runs.md),
  [ADR-011](011-bounded-concurrent-crawl-pipeline.md)

## Контекст

Сетевой сбой, timeout provider-а или невалидный AI-ответ оставляли страницу в состоянии `failed` до
ручного точечного запуска. На больших обходах оператору приходилось повторять каждую строку отдельно,
а временные ошибки снижали полноту БЗ.

## Решение

1. Первая обработка URL считается первой page-level попыткой. После завершения основной очереди
   worker собирает failed pages и выполняет ещё не более двух раундов только для этих URL.
2. Максимум на один run — три page-level попытки. Внутренний транспортный повтор provider-запроса
   остаётся частью одной page-level попытки и не меняет `attempt_count`.
3. Повторы используют те же SSRF, robots, crawl-delay, fetch concurrency, AI concurrency,
   pause/stop и tenant ограничения, что и основной обход. Успешные URL повторно не загружаются.
4. `knowledge_crawl_pages.attempt_count` является checkpoint. Один URL остаётся одной строкой;
   повтор обновляет её, а run counters продолжают считать уникальные страницы.
5. После третьей неудачи run завершается как `partial`. Оператор может одной командой создать новый
   run только из всех failed URL исходного run; новый запуск снова имеет собственный лимит из трёх
   попыток. Точечный повтор одной строки сохраняется.

## Следствия

- Временные ошибки обычно исправляются без участия оператора, но постоянные 4xx, недоступный
  provider или непригодный контент не образуют бесконечный цикл.
- Повторные попытки могут увеличить число сетевых и provider-запросов, максимум до трёх page-level
  обработок одного URL на run.
- Batch retry хранит в BullMQ только идентификатор исходного run; URL заново читаются из tenant-scoped
  строк БД и не принимаются от клиента.
