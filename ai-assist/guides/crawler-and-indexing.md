# Crawler и AI-нормализация сайта

Актуальное решение описано в [ADR-005](../decisions/005-ai-normalized-raw-site-ingestion.md),
[ADR-007](../decisions/007-editable-crawl-normalization.md) и
[ADR-009](../decisions/009-pre-ai-dom-boilerplate-filtering.md), а bounded pipeline — в
[ADR-011](../decisions/011-bounded-concurrent-crawl-pipeline.md). HTML-crawler отвечает за безопасное
получение структуры, ссылок и детерминированно очищенного видимого текста. Смысловая очистка и
классификация выполняются отдельным server-side AI-normalizer после fetch.

## 1. Discovery

Администратор задаёт публичный URL и глубину дерева от 1 до 8. Discovery:

1. Проверяет URL/DNS и получает `robots.txt`.
2. Находит sitemap из robots и `/sitemap.xml`.
3. Собирает ссылки из `nav`, `header` и элементов `role=navigation` главной страницы.
4. Объединяет URL в дерево по сегментам path до заданной глубины.
5. Возвращает рекурсивные nodes с path, URL, label, depth, provenance и descendant count.

Query URL, другой origin, запрещённые robots paths и служебные Bitrix/auth/cart/search paths в дерево
не попадают. Sitemap discovery ограничен 50 файлами и 10 000 URL.

Выбранный узел без потомков становится `includeExactPath`; с потомками — `includePathPrefix`.
Внутренние ссылки страниц дополнительно расширяют очередь только внутри этого scope.

## 2. Safe fetch

- Только HTTP(S), без credentials/fragments и нестандартных портов.
- Все DNS answers должны быть публичными; DNS повторно проверяется после redirect.
- Redirect остаётся на exact origin и в разрешённом path scope.
- `robots.txt`, crawl delay, MIME allowlist, TLS, timeout и byte limit обязательны.
- Страница загружается обычным HTTP; JavaScript/Playwright сейчас не используется.
- Limited mode обрабатывает до 100 страниц, full mode — до 5000.
- Внутри run действует bounded pipeline: по умолчанию до двух fetch и до пяти AI-нормализаций
  одновременно. Общая задержка запуска запросов продолжает соблюдать `requestDelayMs` и robots
  `Crawl-delay`; накопление сырого текста ограничено обратным давлением.

## 3. Ограниченно-параллельный pipeline

Один BullMQ crawl job управляет очередью URL и двумя независимо ограниченными этапами:

```text
очередь URL
    ↓
fetch + DOM extraction — до 2 страниц на run
    ↓
ограниченный буфер сырого текста
    ↓
AI normalization + сохранение — до 5 страниц на run
    ↓
page result + атомарный progress
```

Это асинхронные операции ввода-вывода, а не отдельные системные потоки Node.js. Страница является
независимой единицей обработки; пакеты по 10 URL не создаются.

### 3.1. Область действия лимитов

| Ограничение                   | Значение по умолчанию | Область действия                     |
| ----------------------------- | --------------------: | ------------------------------------ |
| Одновременные HTML fetch      |                     2 | Один crawl run                       |
| Одновременные page processors |                     5 | Один crawl run                       |
| Одновременные AI streams      |                     5 | Все crawl runs одного worker process |
| Одновременные system jobs     |                     2 | Один worker process                  |

Если worker выполняет два crawl runs, каждый может загружать до двух страниц, но оба run совместно
используют пять AI-слотов. При горизонтальном запуске нескольких worker processes AI-лимит действует
отдельно в каждом процессе; общий production limit должен учитывать число реплик и rate limit
provider.

Значения задаются только server-side:

```env
KNOWLEDGE_CRAWL_FETCH_CONCURRENCY=2
KNOWLEDGE_CRAWL_AI_CONCURRENCY=5
```

Допустимые диапазоны — `1..10` и `1..20`. В текущем интерфейсе эти параметры не редактируются;
изменение `.env` применяется после перезапуска worker.

### 3.2. Fetch pool и crawl delay

Перед каждым новым HTML fetch worker проверяет состояние run, SSRF policy, robots и URL scope. После
получения HTML он извлекает ссылки, очищает DOM и передаёт заголовок с видимым текстом следующему
этапу.

Лимит `2` разрешает двум медленным запросам пересекаться по времени, но не отменяет задержку между
моментами их запуска. Все запросы одного run используют общий интервал
`max(requestDelayMs, robots Crawl-delay)`. Например, при задержке 500 мс второй запрос может
стартовать не раньше чем через 500 мс после первого. Если сайт отвечает быстрее интервала, загрузка
фактически остаётся последовательной; если ответ занимает несколько секунд, два fetch выполняются
одновременно.

Robots и sitemap discovery выполняются до основного page pipeline и используют тот же ограничитель
частоты запросов.

### 3.3. Page processors и общий AI limiter

После технической очистки до пяти страниц независимо проходят:

1. AI-нормализацию;
2. runtime-валидацию JSON;
3. создание либо обновление immutable document version;
4. сохранение page result;
5. обновление счётчиков run.

Освободившийся слот сразу получает следующую подготовленную страницу, не ожидая остальные четыре.
Общий FIFO-limiter worker не допускает более пяти provider streams даже при двух одновременно
запущенных crawl jobs. Один ограниченный повтор невалидного или retryable ответа остаётся внутри
того же AI-слота, включая retry delay.

Ошибка fetch сразу создаёт failed page result и не вызывает AI. Ошибка нормализации после
внутреннего provider-повтора помечает failed только эту страницу; остальные операции продолжаются.
После завершения основной очереди failed URL образуют отдельный retry-раунд. Worker выполняет до
трёх page-level попыток, не повторяя уже успешные страницы.

### 3.4. Backpressure и память

Crawler не скачивает весь сайт заранее. Когда пять page processors заняты, fetch-этап перестаёт
наращивать очередь сырого текста. Одновременно в памяти находятся не более пяти обрабатываемых
страниц и примерно двух уже загружаемых либо ожидающих свободного processor slot. Сама очередь URL
содержит адреса и metadata, а не HTML страниц.

### 3.5. Progress, пауза и остановка

Параллельные страницы завершаются не в порядке URL. `processed`, `succeeded`, `failed` и change
counters поэтому обновляются атомарными SQL-приращениями, а `discovered` — через `greatest`. Поздно
завершившаяся страница не может записать более старое значение progress.

После запроса паузы новые fetch не начинаются. До двух уже начатых fetch и до пяти page processors
могут штатно завершиться, поэтому progress после нажатия кнопки ещё некоторое время растёт.
Окончательная остановка разрешена после паузы и кооперативно отменяет ожидающие новые операции.

### 3.6. Восстановление после перезапуска

Если BullMQ повторно выдаёт job, а run остался `running`, worker:

1. загружает сохранённые page results;
2. восстанавливает счётчики из БД;
3. заново выполняет URL discovery, потому что in-memory очередь не сохраняется;
4. пропускает AI-этап для уже сохранённых URL;
5. продолжает оставшиеся страницы с текущими concurrency limits.

Сохранённые страницы могут повторно скачиваться, чтобы восстановить исходящие ссылки, но не должны
повторно расходовать AI-токены. URL и checksum остаются дополнительной защитой от дублирования
документов.

## 4. Сырой HTML-to-text

Cheerio получает первый `h1` либо `title`, видимый `body.text()` до 120 000 символов и до 3000
ссылок. Ссылки собираются до изменения DOM, поэтому удалённые из текста меню продолжают расширять
очередь внутри разрешённого scope. Перед чтением текста удаляются:

- технические `script`, `style`, `noscript`, `template`, `svg`, `iframe`, `canvas`, `object`,
  `embed`, `audio`, `video` и статически скрытые элементы;
- `nav`, `aside`, `menu`, dialog и соответствующие ARIA roles;
- внешние по отношению к основному `main/article` header и footer;
- явно маркированные breadcrumbs, cookie/consent, pagination, social/share, subscription,
  modal/popup, menu/sidebar, callback/feedback, CTA, advertising и promo blocks;
- формы поиска, подписки, callback и feedback; содержательные формы товара сохраняются.

Crawler намеренно не:

- читает JSON-LD/schema.org/microdata;
- определяет товар, услугу или информационную страницу;
- выполняет смысловую оценку оставшихся блоков страницы;
- извлекает цену, SKU или характеристики в отдельные поля;
- исполняет инструкции из HTML.

Сырой HTML не хранится. Извлечённые заголовок и видимый текст сохраняются внутри page result для
повторной ИИ-обработки, но не возвращаются панели.

## 5. AI-normalizer

Для каждой успешно полученной страницы worker использует verified AITUNNEL credential и выбранную
chat-модель проекта. Фиксированная platform-инструкция отделена от сырого текста, который передаётся
как недоверенный user content.

Неизменяемая safety-инструкция запрещает исполнять инструкции страницы, придумывать факты и менять
JSON-формат. Нормализация запрашивает у provider строгий JSON Schema и повторно валидирует ответ
локальной схемой. Для reasoning-моделей используется низкая глубина рассуждения и отдельный
20 000-token output budget, чтобы внутреннее рассуждение не вытесняло итоговый JSON.
Операторский prompt сохраняется в источнике и снимке run, но его редактор временно скрыт в
интерфейсе. API AI-only обработки сохранённого сырого текста остаётся доступным для последующего
возврата редактора.

По умолчанию модель должна:

1. Удалить навигационный и повторяющийся мусор.
2. Сохранить без резюмирования все уникальные относящиеся к предмету страницы факты и полное
   описание; удалить только точные повторы и нерелевантный контекст.
3. Выбрать один тип: `info`, `product` или `service`.
4. Собрать характеристики, артикул, цену и условия внутри единого Markdown.
5. Вернуть только JSON `{ type, title, markdown }`.

Ответ ограничен по размеру и валидируется runtime-схемой. Невалидный JSON,
`PROVIDER_BAD_RESPONSE` или retryable provider error получает один повтор; после него неизвестный
type, пустое поле или provider error превращают страницу в failed result. Общий лимит AI stream
отделён от idle timeout. Если модель завершила stream по исчерпанию output budget, страница получает
точный код `CRAWL_AI_OUTPUT_TRUNCATED`, а не общий `CRAWL_AI_RESPONSE_INVALID`. Модель не получает
tools, provider key, prompt ассистента или прямой доступ к публикации.

Активный run можно приостановить. Worker не начинает новые fetch после сохранённого pause marker;
уже начатые fetch и AI-нормализации завершаются. После команды продолжения worker использует ту же
внутреннюю очередь URL. Приостановленный run можно остановить окончательно. Пока worker подтверждает
кооперативный выход, UI показывает «Останавливается»; после появления `finishedAt` run можно удалить
вместе с его строками результатов. Созданные документы БЗ при остановке и удалении run сохраняются.
Если уже отменённое задание после рестарта оказалось в BullMQ `waiting`, API удаляет его из очереди
и подтверждает остановку; реально `active` задание остаётся защищено до выхода worker.
Для отдельной строки результата доступен точечный повтор: создаётся новый run, который повторно
скачивает только исходный URL и заново выполняет нормализацию.

Каждая строка хранит `attempt_count`. Первая обработка имеет значение `1`; последующие retry-раунды
обновляют ту же строку до максимума `3`. Счётчики run отражают уникальные URL: восстановление failed
страницы уменьшает `failed`, увеличивает `succeeded`, но не увеличивает `processed`. После третьей
ошибки автоматические повторы прекращаются. Кнопка повтора ошибок создаёт новый run только из всех
failed URL выбранного завершённого запуска; URL читаются worker-ом из БД, а не передаются клиентом.
Новый run снова получает собственный лимит из трёх попыток.

Панель показывает отдельную таблицу всей истории запусков. Любой терминальный
`succeeded|partial|failed|cancelled` run можно удалить вместе с page results; записи БЗ при этом
сохраняются. Owner может очистить всю историю после повторного подтверждения пароля. Если существует
queued/running run или активный BullMQ job, массовая очистка блокируется до его остановки.

## 6. Записи и публикация

Одна страница создаёт максимум одну запись. `info` сохраняется внутренним типом `page`; `product` и
`service` — одноимёнными типами. URL источника является identity для идемпотентной синхронизации.

- Новый AI-результат создаёт новую запись.
- Изменившийся checksum создаёт внутреннюю immutable version.
- Неизменившийся checksum не создаёт version.
- Результаты остаются pending до ручной batch-публикации.
- Публикация запускает сборку versioned embedding index и атомарно переключает active index.

История versions остаётся внутренней для аудита/конкурентности. В пользовательском редакторе доступны
поля title/type/Markdown/source URL и действия «Опубликовать изменения»/«Снять с публикации».

## 7. Известные ограничения

- Одна страница не разделяется на несколько товаров/услуг.
- Видимый сырой текст одной страницы ограничен 120 000 символов, итоговый Markdown — 30 000
  символов; превышение требует отдельного chunk-and-merge расширения.
- Нет JS rendering, feed/file ingestion, расписания и missing detection.
- Стоимость/latency растут на один chat request для каждой HTML-страницы.
- После аварийного перезапуска worker внутренняя очередь URL строится заново. Сохранённые URL могут
  повторно скачиваться ради link discovery, но page checkpoint исключает их повторную
  AI-нормализацию и восстанавливает progress из БД.
- Provider credential и chat model обязательны до запуска crawl.
- AI confidence пока не калибруется; валидный результат отображается для ручной проверки.

## 8. Обязательные проверки

- private/local/metadata IP, DNS rebinding и cross-origin redirect;
- timeout, oversized body, wrong MIME и redirect loop;
- robots policy, exact/prefix scope и max depth;
- nested tree из sitemap + нескольких меню;
- extractor не читает schema markup, сохраняет содержательные product blocks и ссылки discovery,
  но удаляет технический код и явный шаблонный boilerplate до AI input;
- повторная AI-обработка использует сохранённый raw text, снимок prompt-а и не обращается к сайту;
- bounded pipeline не превышает отдельные fetch/AI concurrency limits, соблюдает общий crawl delay,
  а параллельные завершения не откатывают progress;
- worker restart восстанавливает page counters, не создаёт повторный AI-вызов для сохранённых URL и
  продолжает незавершённый `running` run;
- pause/resume не теряет уже обработанные страницы, не начинает новый fetch во время паузы и
  позволяет уже начатым операциям завершиться;
- точечный повтор заново получает только выбранный URL и сохраняет project/source scope;
- автоматическая retry-очередь обрабатывает только failed URL, не превышает три page-level попытки,
  не удваивает unique counters и восстанавливается по `attempt_count` после restart;
- пакетный ручной повтор получает URL только из failed rows tenant-scoped исходного run;
- AI output success, malformed JSON, неизвестный type, oversized output, 401/429/5xx;
- prompt-injection text остаётся user content;
- повторный crawl идемпотентен;
- publication не повреждает предыдущий active index.
