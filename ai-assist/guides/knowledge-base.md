# Руководство по базе знаний

## 1. Содержимое записи

Пользовательская модель едина для ручных и автоматически обработанных записей:

- название;
- тип `Инфо | Товар | Услуга`;
- описание в формате Markdown;
- URL источника.

Все подтверждённые характеристики товара/услуги, артикулы, цены, наличие и условия находятся внутри
Markdown. Отдельные structured product fields в новом UI и URL-ingestion не используются. Legacy
`knowledge_products` сохраняется только для обратной совместимости ранее созданных данных.

### Инфо

Сведения о компании, доставке, оплате, возврате, контактах, режиме работы, категориях и другие
статичные страницы, не являющиеся конкретным товаром или услугой. Внутренние типы `page` и `manual`
отображаются как «Инфо».

### Товар

Описание одного конкретного товара. Характеристики оформляются читаемым Markdown-списком или таблицей
без выделения в дополнительные поля формы.

### Услуга

Описание одной конкретной услуги, условий её предоставления и подтверждённых параметров.

## 2. Редактирование и публикация

UI не показывает черновые revisions и историю versions. При создании ручной записи оператор может
вставить обычный несвязный текст или готовый Markdown. Перед сохранением сервер всегда передаёт
исходный текст выбранной chat-модели: она сохраняет все факты, удаляет точные повторы и оформляет
содержимое в Markdown без добавления сведений извне. Только успешно обработанный результат создаётся
и публикуется одним действием; при ошибке ИИ исходная запись в БД не появляется. Для существующей
записи оператор редактирует четыре поля и нажимает «Опубликовать изменения». Отдельная кнопка «Снять
с публикации» немедленно исключает запись из retrieval.

В списке и редакторе доступно необратимое действие «Удалить». Оно требует подтверждения и свежей
проверки пароля, после чего удаляет запись, все версии, публикации, chunks и embeddings. Если chunk
был источником старого ответа виджета, удаляется только техническая ссылка provenance; текст самого
диалога сохраняется. Во время активной индексации удаление блокируется.

В таблице списка есть checkbox каждой строки и общий checkbox всех найденных записей. К выбранным
записям применяются массовая публикация, снятие с публикации или удаление. Таблица находится в
горизонтально прокручиваемом контейнере; динамические название и описание ограничены 320 px и
переносятся, поэтому длинный текст не расширяет страницу.

Внутри системы каждое изменение всё ещё создаёт immutable `knowledge_document_version`, а публикация
атомарно меняет `active_version_id`. Это обеспечивает optimistic concurrency, аудит и безопасный
index snapshot, не усложняя пользовательский workflow.

Sidebar списка содержит «Инструкцию для массовой обработки записей в БЗ». Если строки выбраны,
обрабатываются только они; без выбора — все неархивные записи. Worker передаёт модели текущий title и
Markdown, применяет инструкцию с неизменяемым запретом выдумывать факты и создаёт новую immutable
version. Статус публикации не меняется: для опубликованной записи интерфейс показывает наличие
неопубликованных изменений, пока оператор явно не опубликует последнюю версию.

Под формой отображается сортируемая история запусков с инструкцией, статусом, прогрессом,
инициатором, временем и safe error code. Выполняющийся запуск можно приостановить и продолжить.
Пауза позволяет завершиться уже начатым AI-запросам, но не запускает новые записи. Остановка
доступна для активного запуска независимо от паузы и сохраняет уже созданные версии; после
подтверждения worker-а остановленный или любой другой терминальный запуск можно удалить из истории
без удаления созданных версий БЗ.

Временные ошибки provider-а и некорректный ответ модели автоматически повторяются до трёх раз для
каждой записи. Успешные записи при этом повторно не обрабатываются. Если после исчерпания лимита run
завершился с ошибками, действие «Повторить ошибки» создаёт новый запуск только для failed-записей,
использует ту же инструкцию и их актуальные версии. Запуск повтора недоступен, пока выполняется
другой парсинг, индексирование или постобработка.

Неотправленная инструкция сохраняется отдельно для каждого проекта в состоянии приложения и
localStorage, поэтому не теряется при переходе в другой раздел или перезагрузке. После успешной
постановки обработки в очередь поле очищается; при ошибке текст остаётся для исправления и повтора.

AI-normalized crawl results не публикуются без ручного выбора в результатах обхода.

Owner может выполнить «Очистить записи» либо «Очистить всё». Первая операция удаляет БЗ и все
версии индекса, но сохраняет историю парсинга. Вторая дополнительно удаляет все завершённые запуски
и их постраничные результаты, URL-источники и их настройки. На странице парсинга отдельный источник
или все настроенные источники можно удалить с сохранением уже созданных записей БЗ. Диалоги и audit
log сохраняются при любой из этих операций.

Операторский prompt ИИ-нормализации задаётся при создании URL-источника и сохраняется снимком в
каждом запуске. После технического парсинга его можно изменить и повторно обработать сохранённый
сырой текст без нового запроса сайта. Предыдущий запуск при этом остаётся в истории, а новая
нормализация создаёт отдельные результаты для проверки.

## 3. Выбор структуры сайта

Discovery объединяет `sitemap.xml` и навигационные меню главной страницы и показывает результат как
вложенное раскрывающееся дерево до заданной глубины. Выбор родительского узла включает или снимает
всё его поддерево. При выборе только части дочерних узлов родитель отображается в промежуточном
состоянии.

Перед сохранением полностью выбранные поддеревья сворачиваются в один URL-префикс, а отдельно
выбранные листья сохраняются как точные пути. Это не меняет видимый выбор и не переполняет настройки
источника перечислением каждой дочерней страницы.

## 4. Нормализация и безопасность

- Сырой текст ручной записи всегда проходит AI-нормализацию в Markdown, после чего provider output
  дополнительно нормализуется по Unicode/whitespace.
- Недоверенный HTML сайта сначала превращается crawler-ом в очищенный видимый body text:
  технические DOM-узлы, навигация, внешний header/footer и явно маркированный шаблонный boilerplate
  удаляются, но содержательные product blocks остаются.
- AI-normalizer сохраняет все уникальные относящиеся к странице факты без резюмирования, удаляет
  нерелевантный boilerplate, классифицирует запись и возвращает JSON по строгой схеме.
- Редактируемый prompt не может переопределить неизменяемый запрет выполнять инструкции страницы,
  придумывать факты или менять формат ответа.
- Модель не получает tools/secrets и не может публиковать результат.
- Отсутствующие факты не генерируются.
- URL и тип всегда сохраняются рядом с текстом для provenance.
- `v-html` для knowledge content запрещён; будущий Markdown renderer обязан использовать allowlist
  sanitizer.

## 5. Chunking и retrieval

Title и Markdown объединяются и делятся на chunks до 1200 символов, максимум 40 chunks на version.
Каждый chunk сохраняет project/version identity и checksum.

Retrieval использует только active published version текущего проекта и локали:

1. lexical ranking по опубликованным chunks;
2. query embedding при наличии совместимого active index;
3. vector candidates из pgvector;
4. fusion lexical/vector ranks;
5. lexical fallback при ошибке embeddings.

Новая index version строится в worker и активируется атомарно после проверки fingerprint. Ошибка
индексации не повреждает предыдущий active index.

## 6. Review checklist

- [ ] Название и тип записи корректны.
- [ ] Markdown содержит только подтверждённые факты.
- [ ] Характеристики, цена и наличие не придуманы моделью.
- [ ] Удалены меню, footer, cookie-текст и повторяющиеся CTA.
- [ ] URL источника соответствует содержимому.
- [ ] Нет prompt injection, secrets или персональных данных.
- [ ] После публикации retrieval находит запись по контрольному вопросу.

## 7. Известные ограничения

- Тип записи меняется только при публикации новой внутренней version.
- Одна HTML-страница создаёт максимум одну запись.
- Missing pages не снимаются с публикации автоматически.
- File/feed ingestion и Markdown visual preview ещё не реализованы.
