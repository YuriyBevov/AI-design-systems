# Архитектура проекта Newmark

## Компонентный подход

Компоненты должны быть универсальными и абстрактными. Название компонента и его CSS-класса описывает сущность, а не место использования.

Правильно:

- `Slider`;
- `.slider`;
- `RequestSection`;
- `.request-form`;
- `step-list`.

Неправильно:

- `ContentSlider`;
- `.content-slider`;
- `static-page-slider`;
- `about-slider`, если компонент может использоваться не только на странице о компании.

Если компонент сейчас используется только внутри `.content`, это не повод добавлять в название `content`. Ограничения места использования задаются родительским контекстом, а не именем самостоятельного компонента.

## Slider

`Slider` - самостоятельный универсальный компонент, а не часть контентного блока.

Правила:

- класс компонента - `.slider`;
- компонент может использоваться в Markdown-контенте, карточках, товарных галереях и других зонах сайта;
- слайдер должен оставаться внутри родительского контейнера;
- `freeMode` у Swiper не используется;
- один слайд ограничен `max-width: 400px`.

## Папки Astro

- `src/layouts/` - layout-компоненты, которые задают структуру страницы или общий каркас страницы.
- `src/components/` - переиспользуемые UI-компоненты.
- `src/pages/` - Astro-роуты.
- `src/content/` - Markdown-контент и правила работы с ним.

Главная страница тоже должна использовать общий layout. Нельзя держать в `src/pages/index.astro` собственный `html`, `head`, `body`, `header`, сквозную форму заявки или `footer`: эти части подключаются через `BaseLayout`, `Header`, `RequestSection` и `Footer`.

Крупные повторяемые фрагменты страниц нужно выносить в самостоятельные компоненты. Если блок используется на главной и на отдельной странице, например каталог продукции, он должен жить в `src/components/`, а роуты должны передавать ему только отличающиеся параметры.

Папка `src/templates/` в проекте не используется. Для Astro-страниц достаточно `layouts` и `components`; дополнительный слой `templates` создает путаницу с `layouts`.

## Стили

Единственный источник стилей - `src/styles/main.scss`.

Не нужно создавать или коммитить ручную сборку:

- `src/styles/main.css`;
- `src/styles/main.css.map`.

Astro/Vite собирает SCSS самостоятельно из импорта `../styles/main.scss`.

## Конфигурация сборки

Единственный актуальный конфиг проекта - `astro.config.mjs`.

Vite-настройки задаются внутри поля `vite` в `astro.config.mjs`. Отдельный `vite.config.js` не используется, чтобы не было двух источников правды.

Проект использует `output: "server"` и `@astrojs/node`, потому что формы отправляются через серверный API endpoint. Страницы, которые должны собираться заранее через `getStaticPaths`, должны явно указывать `export const prerender = true`.

SMTP-доступы для отправки форм задаются только через переменные окружения:

- `SMTP_HOST`;
- `SMTP_PORT`;
- `SMTP_SECURE`;
- `SMTP_USER`;
- `SMTP_PASS`;
- `SMTP_FROM`.

Пароли и реальные SMTP-доступы нельзя хранить в репозитории. Для примера структуры используется `.env.example`.

## Package.json

`package.json` должен отражать реальные зависимости проекта, включая зависимости, которые уже заложены в ближайшие реализуемые компоненты.

Правила:

- `@fancyapps/ui` остается в зависимостях, потому что детальная страница товара должна использовать Fancybox/lightbox для галереи;
- `postcss` и `autoprefixer` остаются в devDependencies, потому что проект использует `postcss.config.js` и `.browserslistrc`;
- `vite` не является отдельной сборочной точкой проекта, но может оставаться как peer-зависимость Vite-плагинов;
- не добавлять отдельный `vite.config.js`, даже если в `package.json` есть `vite`;
- перед удалением зависимости нужно проверить ее импорты в `src/`, скрипты, конфиги и ближайшие задачи из ТЗ.

## Шрифты

Шрифты хранятся в `src/fonts/` и подключаются из SCSS через относительные пути.

Не нужно дублировать шрифты в `public/fonts/`. Если файл может быть обработан Astro/Vite из `src`, он должен оставаться в `src`.

## Изображения

Локальные статичные изображения из `src/images/` нужно выводить через Astro `Image`:

```astro
---
import { Image } from "astro:assets";
import imageSrc from "../images/webp/image.webp";
---

<Image src={imageSrc} alt="..." width={400} height={300} />
```

Не нужно импортировать такие изображения как URL через `?url`, если картинка может быть обработана Astro и для нее известны размеры. Это отключает полезную оптимизацию и вызывает предупреждение Astro-аудита `Use the Image component`.

Изображения выше первого экрана должны явно получать `loading="eager"`. Для главного LCP-изображения страницы, например hero-изображения, дополнительно указывается `fetchpriority="high"`. Изображения ниже первого экрана оставляются с ленивой загрузкой.

Нативный `<img>` допустим для динамических строковых путей из данных каталога, внешних URL или случаев, где Astro `Image` не может принять источник без дополнительной подготовки.

## Доступные имена элементов

Заголовки, ссылки и интерактивные элементы не должны оставаться без доступного имени. Имя должно приходить из видимого текста, `aria-label`, `aria-labelledby`, `alt` у изображения внутри ссылки или `title` внутри SVG.

Если текст ссылки или заголовка приходит из данных, компонент обязан иметь безопасный fallback на случай пустого значения.

## SVG-спрайт

Исходные SVG-иконки хранятся в `src/sprite/`.

Спрайт собирается локальным Vite-плагином `scripts/svg-sprite-plugin.mjs`, подключенным в `astro.config.mjs`.

Плагин должен:

- отдавать `/sprite.svg` в dev-режиме до Astro fallback-роутинга;
- записывать `sprite.svg` в `dist/` при `astro build`;
- формировать `symbol id` из имени файла без дополнительного префикса;
- приводить видимые `fill` и `stroke` к `currentColor`, чтобы цвет иконки задавался CSS-классом места использования;
- не менять служебные `mask` и `clipPath`, чтобы не ломать сложные SVG.

В разметке иконки подключаются с версией ресурса: `/sprite.svg?v=2#icon-name`. Если меняется принцип сборки или содержимое спрайта, версию нужно увеличить, чтобы браузер не использовал старый закешированный SVG.

Не нужно хранить собранный `sprite.svg` в `public/`: это сборочный артефакт, а не исходник.

## Клиентский JavaScript

`src/scripts/main.js` только подключает и запускает инициализаторы компонентов.

Правила:

- каждый компонентный скрипт экспортирует функцию `init...`;
- дефолтные селекторы и настройки живут внутри самого модуля;
- `main.js` не должен передавать селекторы без необходимости;
- подключения должны быть однообразными: import init-функции, затем вызов init-функций.

Если компонент требует Swiper, GSAP или другую библиотеку, библиотечная логика остается внутри модуля компонента, а не в `main.js`.

## Модальные окна

Модальное окно - самостоятельный компонент, который подключается через общий layout и открывается по data-атрибутам.

Правила:

- открытие модального окна задается через `data-modal-open`;
- закрытие обязательно работает по кнопке закрытия, клавише `Esc` и клику по оверлею;
- у окна должны быть `role="dialog"`, `aria-modal="true"` и управляемый `aria-hidden`;
- пока окно открыто, фокус и табабельность должны сохраняться внутри модального окна;
- при закрытии фокус возвращается на элемент, который открыл окно;
- если форма открыта из товара, название товара передается в disabled-поле через data-атрибут, остальные формы остаются без товарного поля.
