# Архитектура проекта Newmark

## Компонентный подход

Компоненты должны быть универсальными и абстрактными. Название компонента и его CSS-класса описывает сущность, а не место использования.

Правильно:

- `Slider`;
- `.slider`;
- `RequestSection`;
- `.request-form`;
- `step-list`.

Неправильно:

- `ContentSlider`;
- `.content-slider`;
- `static-page-slider`;
- `about-slider`, если компонент может использоваться не только на странице о компании.

Если компонент сейчас используется только внутри `.content`, это не повод добавлять в название `content`. Ограничения места использования задаются родительским контекстом, а не именем самостоятельного компонента.

## Slider

`Slider` - самостоятельный универсальный компонент, а не часть контентного блока.

Правила:

- класс компонента - `.slider`;
- компонент может использоваться в Markdown-контенте, карточках, товарных галереях и других зонах сайта;
- слайдер должен оставаться внутри родительского контейнера;
- `freeMode` у Swiper не используется;
- один слайд ограничен `max-width: 400px`.

## Папки Astro

- `src/layouts/` - layout-компоненты, которые задают структуру страницы или общий каркас страницы.
- `src/components/` - переиспользуемые UI-компоненты.
- `src/pages/` - Astro-роуты.
- `src/content/` - Markdown-контент и правила работы с ним.

Папка `src/templates/` в проекте не используется. Для Astro-страниц достаточно `layouts` и `components`; дополнительный слой `templates` создает путаницу с `layouts`.

## Стили

Единственный источник стилей - `src/styles/main.scss`.

Не нужно создавать или коммитить ручную сборку:

- `src/styles/main.css`;
- `src/styles/main.css.map`.

Astro/Vite собирает SCSS самостоятельно из импорта `../styles/main.scss`.

## Конфигурация сборки

Единственный актуальный конфиг проекта - `astro.config.mjs`.

Vite-настройки задаются внутри поля `vite` в `astro.config.mjs`. Отдельный `vite.config.js` не используется, чтобы не было двух источников правды.

## Package.json

`package.json` должен отражать реальные зависимости проекта, включая зависимости, которые уже заложены в ближайшие реализуемые компоненты.

Правила:

- `@fancyapps/ui` остается в зависимостях, потому что детальная страница товара должна использовать Fancybox/lightbox для галереи;
- `postcss` и `autoprefixer` остаются в devDependencies, потому что проект использует `postcss.config.js` и `.browserslistrc`;
- `vite` не является отдельной сборочной точкой проекта, но может оставаться как peer-зависимость Vite-плагинов;
- не добавлять отдельный `vite.config.js`, даже если в `package.json` есть `vite`;
- перед удалением зависимости нужно проверить ее импорты в `src/`, скрипты, конфиги и ближайшие задачи из ТЗ.

## Шрифты

Шрифты хранятся в `src/fonts/` и подключаются из SCSS через относительные пути.

Не нужно дублировать шрифты в `public/fonts/`. Если файл может быть обработан Astro/Vite из `src`, он должен оставаться в `src`.

## SVG-спрайт

Исходные SVG-иконки хранятся в `src/sprite/`.

Спрайт собирается локальным Vite-плагином `scripts/svg-sprite-plugin.mjs`, подключенным в `astro.config.mjs`.

Плагин должен:

- отдавать `/sprite.svg` в dev-режиме до Astro fallback-роутинга;
- записывать `sprite.svg` в `dist/` при `astro build`;
- формировать `symbol id` из имени файла без дополнительного префикса.

Не нужно хранить собранный `sprite.svg` в `public/`: это сборочный артефакт, а не исходник.

## Клиентский JavaScript

`src/scripts/main.js` только подключает и запускает инициализаторы компонентов.

Правила:

- каждый компонентный скрипт экспортирует функцию `init...`;
- дефолтные селекторы и настройки живут внутри самого модуля;
- `main.js` не должен передавать селекторы без необходимости;
- подключения должны быть однообразными: import init-функции, затем вызов init-функций.

Если компонент требует Swiper, GSAP или другую библиотеку, библиотечная логика остается внутри модуля компонента, а не в `main.js`.
