# ТЗ на дальнейшее развитие проекта Newmark

Документ описывает следующий этап развития сайта-каталога Newmark: какие шаблоны нужно создать, как должна быть устроена структура каталога и как ИИ должен помогать наполнять сайт новыми страницами, разделами и товарами.

## 1. Цель этапа

Сделать сайт не набором вручную собранных блоков, а управляемой структурой с едиными шаблонами и понятными правилами наполнения.

Основные задачи:

- создать шаблон статичной контентной страницы;
- создать страницу каталога со списком разделов;
- создать шаблон страницы раздела каталога;
- создать детальную страницу товара;
- описать модель данных для наполнения страниц;
- подготовить пошаговые инструкции для ИИ, который будет создавать и обновлять контент.

## 2. Базовые принципы

- У каждой страницы должен быть только один `h1`.
- Структура страниц должна быть предсказуемой: одинаковые сущности наполняются одинаковым набором данных.
- Контент не должен зашиваться хаотично в HTML: для повторяемых сущностей нужны шаблоны и структурированные данные.
- Компоненты должны переиспользоваться: карточка товара, уточнение, список характеристик, хлебные крошки, CTA, галерея, форма заказа.
- ИИ при добавлении контента должен сначала собрать недостающие данные, затем внести изменения, затем проверить страницу по чеклисту.
- Если обязательных данных нет, ИИ не должен придумывать факты. Он должен запросить их у пользователя.
- Все видимые тексты должны соблюдать правила проекта: нормальный регистр, неразрывные пробелы в нужных местах, отсутствие лишних `<br>`, единая типографика.

## 3. Рекомендуемая структура контента

На текущем этапе проект остается статичным. Для управляемого наполнения нужно добавить слой данных и шаблонов.

Рекомендуемый формат для первого этапа:

- данные хранить в `src/content/`;
- страницы и сущности описывать в JSON или Markdown с front matter;
- генерацию HTML выполнять через выбранный шаблонизатор или сборочный скрипт;
- при росте проекта отдельно рассмотреть переход на Astro, Eleventy или другой статический генератор.

Предлагаемая структура:

```text
src/
  content/
    pages/
      about.json
      delivery.json
    catalog/
      sections/
        tpl.json
        packing-tape.json
      products/
        tpl-001.json
        tpl-002.json
  templates/
    static-page.html
    catalog.html
    catalog-section.html
    product.html
  styles/
    pages/
      _static-page.scss
      _catalog.scss
      _catalog-section.scss
      _product.scss
```

Если на этапе реализации будет выбран другой стек, структура может быть адаптирована, но логика должна сохраниться: отдельно данные, отдельно шаблоны, отдельно компоненты.

## 4. Шаблон статичной страницы

Назначение: страницы вроде "О компании", "Доставка", "Оплата", "Производство", "Контакты", "Политика конфиденциальности".

Обязательные зоны:

- `head`: title, description, canonical при необходимости;
- header сайта;
- хлебные крошки;
- один `h1`;
- основной контент;
- CTA или форма, если страница коммерческая;
- footer сайта.

Поддерживаемые контентные блоки:

- текстовый блок;
- блок с изображением;
- список преимуществ;
- нумерованный список этапов;
- таблица или список параметров;
- FAQ;
- CTA-блок;
- блок контактов.

Минимальная модель данных:

```json
{
  "slug": "delivery",
  "title": "Доставка",
  "seoTitle": "Доставка упаковочных материалов Newmark",
  "seoDescription": "Условия доставки упаковочных материалов по России.",
  "breadcrumbs": ["Главная", "Доставка"],
  "h1": "Доставка",
  "lead": "Короткое вводное описание страницы.",
  "contentBlocks": [],
  "cta": {
    "enabled": true,
    "title": "Нужна консультация?",
    "buttonText": "Оставить заявку"
  }
}
```

## 5. Страница каталога

Назначение: верхний уровень каталога, где пользователь видит основные разделы и быстро переходит в нужную категорию.

Обязательные зоны:

- header сайта;
- хлебные крошки;
- один `h1`, например "Каталог";
- вводное описание каталога;
- список разделов каталога;
- блок с преимуществами или условиями работы;
- CTA;
- footer сайта.

Карточка раздела каталога должна содержать:

- название раздела;
- короткое описание;
- изображение или визуальный маркер раздела;
- список ключевых товаров или применений;
- ссылку на страницу раздела.

Минимальная модель данных раздела для страницы каталога:

```json
{
  "title": "ТПЛ",
  "slug": "tpl",
  "description": "Тканевая полиэтиленовая лента для упаковки и технических задач.",
  "image": "src/images/catalog/tpl.webp",
  "imageAlt": "Рулон тканевой полиэтиленовой ленты",
  "features": ["для упаковки", "для ремонта", "для производства"],
  "href": "/catalog/tpl/"
}
```

## 6. Шаблон страницы раздела каталога

Назначение: страница конкретного раздела, например "ТПЛ", "Клейкая лента", "Стрейч-пленка".

Обязательные зоны:

- header сайта;
- хлебные крошки;
- один `h1` с названием раздела;
- описание раздела;
- блок особенностей или применений;
- список товаров раздела;
- уточнения по заказу, если актуальны;
- CTA;
- footer сайта.

Карточка товара на странице раздела должна содержать:

- название товара;
- изображение;
- короткое описание;
- основные характеристики;
- уточнение через компонент `.clarification`, если есть минимальная партия, срок производства или другие условия;
- кнопку перехода на детальную страницу;
- кнопку или ссылку для заказа, если это предусмотрено сценарием.

Минимальная модель данных раздела:

```json
{
  "slug": "tpl",
  "title": "ТПЛ",
  "seoTitle": "ТПЛ оптом от производителя",
  "seoDescription": "Тканевая полиэтиленовая лента для упаковки, ремонта и производства.",
  "h1": "ТПЛ",
  "lead": "Описание раздела и основные сценарии применения.",
  "features": ["высокая прочность", "устойчивость к влаге", "нанесение логотипа"],
  "products": ["tpl-001", "tpl-002"],
  "clarification": "*Минимальная партия — 30 коробок, срок производства — 30 дней"
}
```

## 7. Детальная страница товара

Назначение: дать пользователю достаточно информации, чтобы оставить заявку или связаться с менеджером.

Обязательные зоны:

- header сайта;
- хлебные крошки;
- один `h1` с названием товара;
- галерея изображений со слайдером;
- просмотр изображений через Fancybox или аналогичный lightbox;
- краткое описание;
- основные характеристики;
- условия заказа;
- цена или пояснение, почему цена рассчитывается индивидуально;
- кнопки заказа;
- форма или CTA;
- связанные товары или товары из того же раздела;
- footer сайта.

Основные элементы товара:

- `productGallery` - изображения товара;
- `productSummary` - краткое описание и ключевые условия;
- `productCharacteristics` - таблица или список характеристик;
- `productOrder` - цена, минимальная партия, срок производства, акцизность, кнопки заказа;
- `relatedProducts` - связанные товары.

## 8. Инструкции для ИИ по наполнению

Для каждой сущности нужно создать отдельный гайд:

- `guides/ai-content-global.md` - общие правила контента;
- `guides/ai-static-page.md` - создание статичной страницы;
- `guides/ai-catalog-page.md` - обновление страницы каталога;
- `guides/ai-catalog-section.md` - создание и обновление раздела каталога;
- `guides/ai-product-page.md` - создание и обновление товара;
- `guides/ai-images.md` - правила работы с изображениями;
- `guides/ai-checklist.md` - финальная проверка после изменений.

Каждый гайд должен содержать:

- назначение шаблона;
- список обязательных данных;
- список необязательных данных;
- вопросы, которые ИИ задает пользователю;
- правила именования файлов и slug;
- правила подбора изображений;
- правила SEO-полей;
- чеклист проверки перед завершением задачи.

## 9. Сценарии вопросов для ИИ

### Добавление статичной страницы

ИИ должен запросить:

- название страницы;
- URL/slug;
- основной заголовок `h1`;
- SEO title;
- SEO description;
- вводный текст;
- какие блоки нужны на странице;
- нужен ли CTA;
- нужны ли изображения;
- нужны ли FAQ или таблицы;
- есть ли юридически точные формулировки, которые нельзя менять.

### Добавление раздела каталога

ИИ должен запросить:

- название раздела;
- URL/slug;
- краткое описание раздела;
- полное описание раздела;
- изображение раздела;
- список ключевых особенностей;
- какие товары входят в раздел;
- нужны ли общие условия заказа для раздела;
- SEO title и description, если они уже подготовлены.

### Добавление товара

ИИ должен запросить:

- раздел каталога, куда добавляется товар;
- название товара;
- URL/slug;
- короткое описание;
- полное описание;
- изображения для слайдера;
- alt-тексты изображений;
- характеристики товара;
- цену или тип цены: фиксированная, от, по запросу;
- минимальную партию;
- срок производства;
- является ли товар акцизным;
- доступность товара;
- условия заказа;
- связанные товары;
- SEO title и description.

Если пользователь передал не все данные, ИИ должен разделить вопросы на обязательные и дополнительные. Обязательные нужны для создания страницы, дополнительные можно заполнить позже.

## 10. Правила файлов и slug

- Slug пишется латиницей в нижнем регистре.
- Слова в slug разделяются дефисом.
- Slug должен быть стабильным и не зависеть от временных акций.
- Изображения товара называются по slug товара и номеру: `tpl-armirovannaya-lenta-1.webp`.
- У каждого изображения должен быть осмысленный `alt`.
- Данные товара должны храниться отдельно от данных раздела.
- Раздел каталога содержит ссылки на товары по `id`, а не полные копии данных товара.

## 11. SEO и семантика

- На каждой HTML-странице допускается только один `h1`.
- `title` и `h1` могут отличаться: `title` решает SEO-задачу, `h1` должен быть понятным пользователю.
- У каждой страницы должен быть уникальный `meta description`.
- Хлебные крошки должны соответствовать структуре сайта.
- Карточки товаров и разделов должны иметь понятные ссылки с доступным текстом.
- Таблицы характеристик используются только для табличных данных; если данные простые, допустим список.

## 12. Этапы реализации

### Этап 1. Подготовка структуры

- выбрать формат данных: JSON, Markdown front matter или другой подход;
- создать папки для контента;
- создать базовые шаблоны;
- подключить сборку страниц;
- описать правила генерации URL.

### Этап 2. Шаблоны страниц

- реализовать шаблон статичной страницы;
- реализовать страницу каталога;
- реализовать шаблон раздела каталога;
- реализовать детальную страницу товара;
- вынести общие элементы в компоненты.

### Этап 3. Компоненты товара

- реализовать галерею товара;
- подключить Fancybox или аналогичный lightbox;
- реализовать блок характеристик;
- реализовать блок условий заказа;
- реализовать блок связанных товаров;
- проверить мобильную адаптацию.

### Этап 4. AI-гайды

- создать глобальный гайд по наполнению;
- создать гайды для каждого типа страницы;
- создать чеклист контроля качества;
- добавить примеры заполненных данных;
- описать сценарии вопросов к пользователю.

### Этап 5. Проверка

- собрать проект;
- проверить страницы на валидную семантику;
- проверить, что на странице только один `h1`;
- проверить адаптацию на мобильных ширинах;
- проверить изображения и alt-тексты;
- проверить, что контент не ломает сетку;
- проверить `npm run build`.

## 13. Критерии приемки

Работа считается выполненной, когда:

- есть четыре рабочих типа страниц: статичная, каталог, раздел каталога, товар;
- каждый тип страницы собирается из шаблона и структурированных данных;
- для каждого типа страницы есть AI-гайд по наполнению;
- ИИ может добавить новый товар, задав пользователю понятные вопросы;
- карточки и детальные страницы используют единые компоненты;
- галерея товара работает со слайдером и Fancybox;
- все страницы сохраняют правило одного `h1`;
- проект успешно собирается командой `npm run build`;
- добавление нового товара не требует ручного копирования больших HTML-фрагментов.

## 14. Открытые решения перед реализацией

Перед началом разработки нужно выбрать:

- оставляем текущую Vite-структуру и добавляем собственную генерацию страниц;
- переходим на статический генератор вроде Astro или Eleventy;
- какой формат данных использовать для контента;
- где будут храниться исходные изображения товаров;
- нужна ли в будущем интеграция с внешней CMS или достаточно AI-управляемых файлов в репозитории.

Рекомендуемое решение для ближайшего этапа: не усложнять проект CMS, а начать с файловой модели данных и шаблонов. Это даст ИИ понятные правила, сохранит контроль через Git и позволит позже безболезненно перейти на более мощный генератор, если каталог вырастет.
