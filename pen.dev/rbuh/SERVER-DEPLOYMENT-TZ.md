# Техническое задание на размещение сайта РБУ «Хаджох» на сервере

Дата: 7 сентября 2026 года.

Статус: ТЗ подготовлено; параметры сервера, домена и почты необходимо согласовать до развёртывания. Этот документ описывает предстоящие работы и не подтверждает их выполнение на сервере.

## 1. Цель и границы работ

Разместить текущую сборку сайта на согласованном сервере, подключить домен и HTTPS, обеспечить постоянную работу приложения и доставку заявок на почту. Передать заказчику работающий сайт, результаты проверки и инструкцию сопровождения.

Сохранить существующие страницы, URL, дизайн, адаптив, тексты, изображения, шрифты и интерактивные элементы. Не переводить сайт на другой стек, не заменять серверный обработчик формы и не устанавливать CMS без отдельного согласования.

Разделить работы на два этапа:

1. Техническое размещение и проверка на закрытом тестовом адресе.
2. Публичный запуск после настройки почты, приёмки и разрешения заказчика.

Составление юридических документов, заполнение прайса, SEO-доработки, покупка хостинга и изменение контента в объём размещения не входят. Возникающие дополнительные работы согласовываются отдельно.

## 4. Требования к среде

Проект использует Astro 7 и `@astrojs/node` в режиме `standalone`, `output: "server"`. Приложение обслуживает серверные страницы, статические ресурсы и `POST /api/send-request`. Размещение только `dist/client` либо загрузка архива в обычный каталог HTML/PHP-хостинга не обеспечивает работу текущего сайта. Поведение режима: [документация Astro Node](https://docs.astro.build/en/guides/integrations-guide/node/#standalone).

Требования:

- Linux-сервер или управляемый хостинг с поддержкой постоянного Node.js-процесса.
- Актуальный патч Node.js 24 LTS; ветка закреплена в `.nvmrc`. Минимум зависимостей — Node.js 22.12.0 и npm 9.6.5. Статус поддержки проверяется по [списку релизов Node.js](https://nodejs.org/en/about/previous-releases).
- Достаточно памяти для запуска приложения и установки зависимостей, места для двух релизов, резервных копий и логов. Потребление ресурсов фиксируется при проверке; нагрузочная гарантия без данных о посещаемости не устанавливается.
- Обратный прокси Nginx либо аналогичная функция панели хостинга, HTTPS и автоматическое продление сертификата.
- Автозапуск и восстановление процесса после сбоя через systemd или штатный менеджер приложений хостинга.
- Доступ сервера к npm при установке зависимостей и к согласованному SMTP-серверу при отправке писем.

Отдельные БД, Redis и файловое хранилище заявок для текущей версии не требуются. Заявки передаются по SMTP; собственного архива заявок в приложении нет.

## 5. Подготовка и установка

1. Проверить среду и права доступа, свободный порт, занятое дисковое пространство и соседние приложения. Не менять глобальную версию Node.js, общие правила прокси или настройки других сайтов без согласования.
2. Сохранить предыдущий сайт, конфигурацию приложения и прокси, действующие DNS-записи и серверные переменные окружения. Резервные копии с секретами хранить отдельно от публичных файлов с ограниченным доступом.
3. Подготовить новую отдельную папку релиза. Не распаковывать архив поверх работающей версии и не удалять её до приёмки.
4. Загрузить архив и файл SHA-256. Проверить контрольную сумму; при несовпадении остановить установку.
5. Распаковать архив, сохранив структуру `dist/client` и `dist/server`. Установить production-зависимости на целевом сервере из lock-файла. Не переносить `node_modules` с macOS и не выполнять `npm update`.
6. Создать серверный `.env` из `.env.example` или перенести подтверждённую конфигурацию из предыдущей версии. Назначить владельцем пользователя приложения, ограничить права чтения.
7. Запустить приложение под непривилегированным пользователем. Рабочей директорией должна быть папка нового релиза; команда запуска — `npm start`.
8. Проверить прямой локальный запуск, затем тестовый адрес через HTTPS-прокси. Только после этого переходить к публичному переключению.

Команды проверки архива и установки выполняются в новой папке релиза, куда загружены оба файла:

```sh
sha256sum -c rbuh-server.tar.gz.sha256
tar -xzf rbuh-server.tar.gz
npm ci --omit=dev
```

После подготовки `.env` команда `npm start` запускает `dist/server/entry.mjs` и загружает переменные из `.env`. Готовый архив не требует повторной сборки на сервере.

Если нужна новая сборка из исходников, выполнить `npm ci` и `npm run release` в папке `pen.dev/rbuh` согласованного коммита. Это отдельный шаг подготовки релиза, а не способ запуска готового архива.

## 6. Переменные окружения и заявки

| Переменная | Значение или назначение |
| --- | --- |
| `NODE_ENV` | `production` |
| `HOST` | `127.0.0.1` при прокси на том же сервере; другое значение — по требованиям хостинга |
| `PORT` | По умолчанию `4321`; при конфликте назначить свободный порт и обновить прокси |
| `SMTP_HOST` | Подтверждённый адрес почтового сервера |
| `SMTP_PORT` | Порт из настроек почтового провайдера |
| `SMTP_SECURE` | Режим подключения согласно настройкам провайдера |
| `SMTP_USER` | SMTP-логин |
| `SMTP_PASS` | SMTP-пароль, только на сервере |
| `SMTP_FROM` | Разрешённый адрес отправителя; при пустом значении приложение использует `SMTP_USER` |
| `SMTP_TO` | Подтверждённый адрес получения заявок |

Проверить отсутствие устаревших переменных в панели или службе запуска: внешние переменные имеют приоритет над `.env`. После изменения конфигурации перезапустить приложение.

Проверить обе формы — на странице и в модальном окне:

- Поля: имя, телефон, комментарий; комментарий необязателен. Согласие на обработку персональных данных обязательно.
- Валидная заявка с согласованными тестовыми данными возвращает HTTP 200 и `{"ok":true}`; письмо фактически приходит на `SMTP_TO` с темой «Заявка с сайта РБУ «Хаджох»».
- Содержимое письма соответствует введённым данным, включая комментарий и согласие. Отображается сообщение об успехе.
- Пустые обязательные поля или отсутствие согласия не приводят к отправке. Серверная валидация возвращает HTTP 400.
- При недоступной почте отображается ошибка, а не ложный успех. Без SMTP-конфигурации endpoint возвращает HTTP 503; ошибка отправки — HTTP 500.

Негативные проверки SMTP проводить на тестовой копии, не отключая почту работающего сайта. Проверка HTTP-ответа не заменяет подтверждение получения письма. Недоставленные заявки приложение самостоятельно не сохраняет и повторно не отправляет.

## 7. Домен, HTTPS, прокси и безопасность

1. Привязать подтверждённый домен к приложению. Менять только согласованные записи DNS; не затрагивать существующие MX и почтовые TXT-записи. IPv6 настраивать только при его фактической доступности.
2. Выпустить сертификат для нужных имён, включить автоматическое продление и проверить его механизм. Основной сайт должен открываться по HTTPS без предупреждений и смешанного содержимого.
3. Настроить постоянное перенаправление HTTP на HTTPS и дополнительного имени на основное с сохранением пути и параметров. Не допускать циклов и длинных цепочек редиректов.
4. Направить все URL, включая `/api/send-request`, `/_astro/` и `/_image`, в Node-приложение. Не использовать SPA-fallback, который возвращает главную страницу на любой URL. Несуществующий маршрут должен отвечать HTTP 404.
5. Сохранить внешний `Host`, передавать корректные сведения об исходном протоколе и клиенте через доверенный прокси; входящие forwarded-заголовки должны нормализоваться инфраструктурой. Требования к переопределению заголовков: [Nginx proxy_set_header](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header).
6. Проверить отправку формы именно с публичного HTTPS-домена. При ошибке Origin/403 проверить прокси и доверенные имена, а не отключать защиту. Если понадобится `security.allowedDomains`, согласовать настройку конкретных доменов и новую сборку с разработчиком. Назначение настройки: [Astro security.allowedDomains](https://docs.astro.build/en/reference/configuration-reference/#securityalloweddomains).
7. Не открывать внутренний Node-порт в интернет при локальном прокси. Приложение запускается не от root; доступ к SSH и панели ограничивается согласно правилам владельца сервера.
8. Запретить публичную раздачу корня релиза, `.env`, `.git`, архивов, исходников, `node_modules` и `dist/server`. Не включать листинг каталогов. Закрытые файлы при HTTP-проверке возвращают 403/404, но не содержимое.
9. Не кэшировать POST-запросы и ответы формы; не включать общий прокси-кэш HTML без отдельной настройки. Не задавать правила безопасности, которые ломают iframe Яндекс Карт, формы, шрифты или скрипты.
10. Настроить ротацию логов и наблюдение за HTTP 5xx, остановкой процесса и сроком сертификата. Не записывать SMTP-пароли и тела заявок в общедоступные логи. Получателя уведомлений согласовать с заказчиком.

## 8. Условия публичного запуска

Тестовый адрес до приёмки закрыть авторизацией или сетевым ограничением; дополнительно запретить индексацию. Один `robots.txt` не является защитой доступа. На основном сайте после разрешения запуска убрать тестовые ограничения и проверить отсутствие случайного `noindex`.

Зафиксировать с заказчиком состояние контента до открытия сайта:

- Полный прайс и условия доставки ещё не заполнены окончательно.
- Реквизиты, политика конфиденциальности и оферта содержат временные тексты; заказчик должен предоставить или согласовать итоговые документы до публичного приёма заявок.
- Точный адрес и ссылки MAX/WhatsApp требуют подтверждения. Не подставлять вымышленные данные.
- Текстовые отзывы и аватары были сгенерированы для макета; они не являются проверенными клиентскими отзывами. Их замену подтверждёнными материалами согласовать с владельцем до публичного запуска.

Эти согласования не предполагают самостоятельной правки публичных текстов или добавления надписей о демо. Техническую проверку можно провести на закрытой копии.

В текущем проекте есть разрешающий `robots.txt`, но не задан основной домен в Astro, canonical не заполнены, sitemap не сформирован. Подготовку canonical и sitemap после подтверждения домена оформить отдельной задачей разработчику; не считать её автоматически выполненной при настройке DNS и HTTPS.

## 9. Приёмочные проверки

### Страницы и ресурсы

Все маршруты ниже должны открываться напрямую и после обновления страницы с HTTP 200:

```text

/price/

/delivery-payment/
/policy-privacy/
/offer/

/services/proizvodstvo-i-dostavka-betona/
/services/laboratornoe-soprovozhdenie/
/services/uslugi-avtobetononasosa/
/services/dostavka-inertnyh-materialov/
```

Проверить:

- Отсутствуют ошибки загрузки локальных CSS, JS, изображений, шрифтов Exo 2 и SVG-спрайта; favicon и `robots.txt` доступны.
- На страницах по одному `h1`; нет дублирования документа или повторной шапки/футера после серверного рендеринга.
- На каждой странице форма находится внутри `main`, перед картой. Карта использует текущий iframe и сохраняет `scroll=false`.
- Неизвестный URL возвращает 404. Секреты и серверные файлы не доступны по HTTP.

### Внешний вид и взаимодействие

Сравнить с согласованной сборкой на ширинах 320, 768, 1024 и 1440 px в актуальных Chrome и Safari:

- Сохранены шапка, футер, меню, шрифты, графитово-стальная палитра, отступы и изображения. Не появляется горизонтальная прокрутка всей страницы; широкие таблицы прокручиваются внутри своего блока.
- Базовые карточки услуг имеют `min-height: 380px` без фиксированного `aspect-ratio`; компактный вариант в «Других услугах» сохраняется.
- Работают мобильное меню, FAQ, модальные окна, слайдеры, пагинация, стрелки и кнопка возврата наверх.
- Таймер считает до 21:00 по Москве, равен нулю с 21:00 до 08:00 и запускается в 08:00; дни скрыты. Проверить границы времени на тестовой копии без изменения системных часов production-сервера.
- Обе формы проходят проверки из раздела 6 на HTTPS-адресе. Телефон и почтовая ссылка используют текущие контакты.

### Устойчивость

- Приложение продолжает работу после закрытия SSH-сессии.
- После остановки/сбоя процесса менеджер восстанавливает его. Автозапуск после перезагрузки сервера проверен в согласованное окно; перезагрузка общего сервера без разрешения недопустима.
- В течение контрольных 30 минут после переключения нет повторяющихся падений процесса и HTTP 5xx на проверяемых страницах.
- Фактические потребление памяти, свободное место, путь к логам и способ получения уведомлений отражены в отчёте.

Локально для указанного релиза уже проверены запуск на Node.js 24, 12 страниц, загрузка ресурсов и ответы формы без отправки писем. Это не заменяет приёмку на целевом сервере, проверку внешнего HTTPS-прокси и фактической доставки почты.

## 10. Переключение и откат

Переключать основной домен или прокси на новый релиз только после предварительных проверок и согласования окна работ. Старую версию сохранить до завершения приёмки и согласования срока хранения.

До переключения исполнитель фиксирует способ возврата: предыдущая папка релиза, конфигурация процесса/прокси, резервные DNS-записи и ответственный. Изменение DNS не гарантирует мгновенного отката из-за кэшей; где возможно, переключать приложение внутри сервера без повторной смены DNS.

Основания для отката: сайт недоступен, массовые 404/5xx, не загружаются основные ресурсы, не отправляются заявки или нарушена утверждённая вёрстка.

При откате восстановить предыдущую конфигурацию процесса/прокси и версию приложения, перезапустить службу, проверить главную, внутреннюю страницу и форму. Не восстанавливать заведомо устаревшие или отозванные SMTP-секреты. Если предыдущего сайта нет, закрыть неисправный запуск, уведомить заказчика и сохранить логи для диагностики. Не удалять материалы для разбора причины сбоя.

## 11. Результат работ и передача заказчику

Исполнитель передаёт:

1. Адрес работающего сайта и подтверждение согласованного основного домена.
2. Коммит, SHA-256 установленного архива, дату запуска и путь к папке релиза.
3. Версии Node.js/npm, системного пользователя, имя службы и внутренний порт; команды запуска, остановки, перезапуска и просмотра логов для фактической среды.
4. Описание настроек прокси, HTTPS, продления сертификата, резервного копирования и уведомлений; без паролей и закрытых ключей.
5. Чеклист выполненных проверок с результатами, включая подтверждение получения тестового письма из каждой формы.
